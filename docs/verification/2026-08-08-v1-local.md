# V1 local verification — 2026-08-08

This report characterizes one local run. It is evidence for correctness and a baseline for later experiments, not a production capacity or high-availability claim.

## Environment

- Host: Apple M4, arm64, 16 GiB RAM, macOS 26.5.
- Application runtime: OpenJDK 21.0.12, Maven 3.9.16.
- Database runtime: MySQL 8.4.6 in Docker Desktop 29.4.1; Docker allocated about 7.75 GiB.
- Load generator: k6 2.1.0 on the same host as the application and database.
- Application: one Spring Boot process, default conditional-atomic strategy, Hikari maximum pool size 20, transaction retry budget 5.

## Correctness gate

Command: `mvn test` with Java 21 and Testcontainers MySQL 8.4.6.

- 20 tests run; 0 failures, 0 errors, 0 skipped.
- Flyway migration and database constraints passed.
- Deterministic unsafe lost-update control passed.
- Concurrent same-key and same-user idempotency tests passed.
- Payment/expiration ordering and expiration rollback tests passed.
- Conditional atomic, pessimistic, and optimistic strategies each preserved invariants under 25 coordinated requests for 5 units.
- The run exposed real InnoDB deadlocks before bounded whole-transaction retry was added. Retrying only the failed SQL was deliberately rejected.

## HTTP characterization

The disposable dataset contained one active SKU with 1,000 units. After the correctness gate passed, the application was run locally and k6 executed:

`k6 run -e SKU_ID=demo-sku -e VUS=20 -e DURATION=30s load-tests/synchronous-orders.js`

| Measure | Result |
|---|---:|
| Requests | 9,357 |
| Request rate | 311.35 requests/second |
| Mean latency | 64.01 ms |
| p90 latency | 81.10 ms |
| p95 latency | 88.80 ms |
| Maximum latency | 187.02 ms |
| 201 created | 1,000 |
| 409 business rejection | 1,668 |
| 503 retryable overload/contention | 6,689 |
| Unexpected status checks | 0 |

k6 treats 201, 409, and 503 as expected protocol responses because each is part of the documented API contract. The separate counters are essential: 6,689 retryable 503 responses show that this configuration saturates under this closed-loop workload. Therefore the request-rate number must not be presented as successful-order throughput or as a production target.
